# Feature Specification: 服务端源码改为 TypeScript

**Feature Branch**: `006-server-to-typescript`

**Created**: 2026-10-17

**Status**: Draft

**Input**: User description: "server代码改为ts"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 服务端业务源码改为可在运行前检查类型的写法 (Priority: P1)

维护服务端的人今天改的是一套没有类型检查的源码，写错字段、写错参数要等到真正跑起来才发现。本次之后，服务端里会在运行时执行的业务与启动源码，全部改为 TypeScript，并且纳入类型检查。写错数据类型时，在发布之前就能被拦住。

**Why this priority**: 这是本次要交付的变化。电脑网页和小程序已经用 TypeScript 维护，服务端仍是另一套写法，改接口或改字段时只能靠人工对照。先把服务端源码统一过来，后面的修改才有同一套检查可依。

**Independent Test**: 只看服务端源码和一次类型检查，不要求先改电脑网页或小程序。确认运行时会执行的业务与启动源码都已是 TypeScript，故意改错一处类型后检查失败，改回后检查通过。

**Acceptance Scenarios**:

1. **Given** 服务端仍有需要维护的 JavaScript 业务或启动源码，**When** 本次交付完成，**Then** 这些源码都改为 TypeScript，维护者不再需要在 JavaScript 里改业务规则。
2. **Given** 维护者在服务端源码里写错了一处明确的数据类型，**When** 执行类型检查，**Then** 检查失败，并指出出错位置，该版本不能当作可发布版本。
3. **Given** 类型错误已经改回，**When** 再次执行类型检查，**Then** 检查通过。
4. **Given** 某个外部依赖没有现成的类型描述，**When** 转换完成，**Then** 只在该依赖的边界做最小标注使检查可以通过，对应的业务规则本身仍是接受检查的 TypeScript，而不是整段留在旧写法或整文件放弃检查。

---

### User Story 2 - 记账的人感觉不到这次改动 (Priority: P1)

家人继续用电脑网页或微信小程序记账。登录、看账本、记一笔、改自己的账、删自己的账、用分享码加入，步骤和结果与改动前相同。已经记下的账还在，金额、记账人、归属人不变。这次只换服务端的编写方式，不改记账规则，也不改对外怎么调用。

**Why this priority**: 源码语言换了，如果账丢了、权限松了，或电脑与小程序对不上，家庭账本就没法继续用。保住现有行为和已有数据，与换成 TypeScript 必须同时成立。

**Independent Test**: 改动前记下某个账本的成员、一笔已知明细的金额、记账人和归属人。改动并重新启动后，用同一账号分别在电脑网页和小程序打开该账本，核对这笔明细仍在且内容一致；再各完成一次「记一笔」和「只有记账人能改自己的账」，结果与改动前相同。

**Acceptance Scenarios**:

1. **Given** 某账本在改动前已有成员和收支明细，**When** 服务端改为 TypeScript 并重新提供服务，**Then** 这些成员和明细仍可在电脑网页与微信小程序中看到，笔数、金额、记账人、归属人与改动前一致。
2. **Given** 一笔明细是成员甲记下的，**When** 甲在电脑网页或小程序中编辑或删除它，**Then** 仍只有甲可以改、可以删，其他成员不行。
3. **Given** 用户要登录、新建或进入账本、用分享码邀请家人、记一笔支出或收入、查看流水，**When** 在改动前可用的入口上操作，**Then** 能做的事与改动前相同，没有新增也没有减少。
4. **Given** 用户已在小程序绑定过微信，**When** 改动后打开小程序，**Then** 仍按原方式自动登录，不需要重新注册或重新绑定。
5. **Given** 同一笔请求在改动前会成功或会按原有原因失败，**When** 改动后用同样的方式再次请求，**Then** 成功时业务结果一致，失败时用户能理解的原因不变。

### User Story 3 - 按部署说明仍能把服务开起来 (Priority: P2)

负责发布的人按现有部署说明启动服务。对外仍是原来的地址，密钥仍放在原来的环境配置里，不需要把密钥写进源码。若因为源码语言变化，说明里的启动步骤或文件名已经对不上，本次必须把说明改到能照着做；照着做可以在一次常规发布里把服务启动起来。电脑网页和小程序不用因此更换接口地址。

**Why this priority**: 源码换了语言，如果发布的人无法启动，或启动后地址变了，前面的类型检查对使用者没有意义。它依赖故事 1 的源码已经可以运行，所以排在后面。

**Independent Test**: 只按更新后的部署说明，在已有数据库和缓存可用的环境里启动服务，用改动前的地址访问，确认电脑网页和小程序仍能连上，且环境配置仍只放在原位置。

**Acceptance Scenarios**:

1. **Given** 发布人员手中是本次交付附带的部署说明，**When** 按说明启动服务，**Then** 服务能在一次常规发布内启动，电脑网页和小程序继续使用原来的接口地址。
2. **Given** 密钥和数据库口令原来放在服务端环境配置中，**When** 本次交付完成，**Then** 它们仍只放在该处或进程环境中，不出现在可提交的源码里。
3. **Given** 部署说明里提到的启动步骤或源码文件名因本次改名而不再正确，**When** 交付完成，**Then** 说明已改为当前可执行的步骤，按旧文件名不会被当成仍有效的步骤留下。

---

### Edge Cases

- 环境配置缺少密钥或数据库口令时，服务仍不能带着空密钥正常对外提供记账；不得因为换成 TypeScript 就改成静默启动成功。
- 发布需要重启服务。重启完成后，密钥未变，原有登录在原先的有效期内仍然有效，不要求全家重新注册。
- 改动前已经加密保存的内容，改动后仍能按原规则读出，不要求用户重新录入。
- 数据库里的表和已有账本数据保持原样，本次不要求导入、导出或结构调整。
- 图片、导出、智能解析等已经提供的能力，改动后仍按原有方式可用；本次不新增能力，也不下线这些能力。
- 手机浏览器里的记账网页保持关闭，不因本次服务端改动而恢复。
- 转换过程中不允许一部分业务规则永久留在 JavaScript、另一部分改为 TypeScript 作为最终状态。
- 类型检查未通过的版本不得当作可发布版本；检查通过但业务结果与改动前不一致，同样不得发布。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 服务端中会在运行时执行的业务源码和启动源码，必须改为 TypeScript。交付完成时，这些源码不再以 JavaScript 作为维护形态。
- **FR-002**: 类型检查必须覆盖上述源码。出现明确的类型错误时，检查必须失败，并且失败版本不得作为可发布版本。
- **FR-003**: 外部依赖缺少类型描述时，只允许在该依赖边界做最小标注以使检查通过。业务规则必须仍接受类型检查，不得整文件放弃检查，也不得因此把该段业务留在 JavaScript。
- **FR-004**: 电脑网页、微信小程序，以及已经关闭的手机网页，不在本次改动范围内。手机网页不得恢复。
- **FR-005**: 对外调用的地址、必填项、已有结果字段和用户能理解的失败原因必须与改动前一致。本次不得新增、删除或改变记账能力。
- **FR-006**: 账本之间的隔离、记账人不可更改、只有记账人能改删自己的明细、归属人规则、分享码加入，以及小程序的绑定和自动登录，必须与改动前一致。
- **FR-007**: 已有账本、成员、明细、预算、计划和绑定关系必须原样保留，改动后无需重新录入或重新加入。
- **FR-008**: 数据库表结构不得因本次改动而变化。
- **FR-009**: 密钥与数据库口令必须继续只放在既有环境配置或进程环境中，不得写入可提交源码。
- **FR-010**: 服务启动后，电脑网页和小程序必须仍能使用原来的接口地址。若部署说明中的启动步骤或文件名不再正确，必须在同一次交付中改正，使按说明可以完成一次常规发布。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用改动前已有的账号，完成登录、打开已有账本、记一笔、修改自己的一笔、用分享码加入账本，五项全部成功，且规则与改动前一致。
- **SC-002**: 抽查改动前已存在的至少一笔明细，重启后在电脑网页和小程序中都能看到，金额、记账人和归属人与改动前一致。
- **SC-003**: 维护者故意写错一处服务端数据类型时，发布前的检查失败并指出位置；改回后检查通过。未通过检查的版本不被当作可发布版本。
- **SC-004**: 交付完成时，服务端运行时业务与启动源码中，不再有仍需用 JavaScript 维护的文件。
- **SC-005**: 发布人员按本次交付的部署说明操作，能在一次常规发布内启动服务；电脑网页和小程序无需更换接口地址即可继续完成 SC-001 中的操作。
- **SC-006**: 抽查至少一项改动前就会拒绝的操作（例如未登录就记账），拒绝原因与改动前一致，使用者不会看到一套新的、无法理解的报错来替代原有提示。

## Assumptions

- 「server代码」指服务端里会在运行时执行的业务源码和启动源码。依赖包、日志、环境配置、数据库脚本、进程清单和代码格式化配置不改写成 TypeScript。
- 本次不改变产品功能，只改变服务端源码的编写与检查方式。电脑网页和小程序的功能和源码不在范围内。
- 项目当前没有服务端自动化测试套件。本次不新增「必须达到某种测试覆盖率」的要求。验收以类型检查，以及关键记账路径与改动前一致为准。
- 类型检查有多严、用哪一种启动方式把 TypeScript 跑起来，留给规划决定。规格只要求：业务源码纳入检查，明确的类型错误能在发布前拦住，且使用者看到的行为不变。
- 对外约定保持向后兼容。本次不批准改变接口形状或数据库表结构。
- 宪章里服务端一行描述的是现有运行时职责，没有单独规定源码语言。本次不改变电脑网页、小程序、服务端这三端的分工。是否把「服务端源码使用 TypeScript」写进宪章，由规划阶段判断。
- 部署说明里如果写死了即将改名的源码文件，随本次更正；密钥位置和对外地址不改。面向家人的使用手册不因源码语言变化而改写操作步骤。
