# Research: 概览统计支持多人分账

## 1. 分账在浏览器算，还是在服务端算

**Decision**: 在服务端计算。电脑端查询时把数量和数量规则的归属人交给新接口，单价和「指定支出类型」规则以账本中已保存的为准。公共支出先加总，再按权重只分一次。现有 `GET /api/v1/overview/balance` 仍只返回总支出、总投资、总收入和按人加总的明细，字段含义不变。

**Rationale**: 垫付和归属必须看每一笔记账，汇总接口没有这些明细。公共支出若逐笔四舍五入再相加，多笔都除不尽时总账会偏离「总额只分一次」。数量是查询时才填的，不能提前写进账本；单价若由浏览器上报，可以被改掉。

**Alternatives considered**:

- 只改电脑端、继续用汇总接口：两人整元例子能对上，但看不到每笔的记账人和归属人。
- 逐笔四舍五入再相加：单笔能轧平，笔数一多，总账误差会叠上去。
- 浏览器把记账列表拉全再自己算：记账列表现有单次上限是 1000 条，算法还会和任何以后的服务端修正各写一份。

## 2. 新接口还是扩出现有汇总接口

**Decision**: 新增 `POST /api/v1/overview/settlement`。不往 `GET /balance` 或 `GET /threeYearCost` 里加结算字段，也不改它们的查询参数。

**Rationale**: 手机网页和小程序今天用汇总接口看总支出等数字。规格要求这两端不增加分账，已有汇总口径不变。新路径对旧客户端是不可见的，回滚时去掉该路径即可，没有表要迁。

**Alternatives considered**:

- 在 `GET /balance` 上增加可选查询参数和可选响应字段：手机端不读新字段也能工作，但数量规则用查询字符串不好表达，而且把两套口径绑在一个已被多端调用的接口上。

## 3. 成员顺序和「最后一名」

**Decision**: 分摊和转账匹配使用 `bill_users.id` 升序。结算响应里的 `members` 按这个顺序给出。轧差的最后一名是这个数组的最后一名当前成员。不修改账本详情里 `users` 的返回顺序。

**Rationale**: `bill_users` 没有创建时间，账本详情今天查询成员时也没有 `ORDER BY`，两次读取的先后不能当合同。规格里的整元例子不依赖谁排在最后。分位上的 1 分必须稳定，所以结算自己规定一个不变的顺序。改账本详情的成员顺序会牵动记账页的下拉，本次不做。

**Alternatives considered**:

- 跟随账本详情数组的偶然顺序：同一笔账两次查询，最后一名可能对调。
- 按姓名排序：改昵称会改变谁吸收那 1 分。

## 4. 怎样分一笔公共支出，才不会出现负数

**Decision**: 金额先换成整数「分」。归属为「全部」的支出先加总，再对这个总额分一次。当前成员按上一节的顺序，除最后一名外，份额为「总额 × 该人权重 / 权重和」后四舍五入到分；若这个数大于尚未分出的金额，就只取剩余。最后一名取得剩下的全部分。权重为 0 的人在这一步得到 0。全体权重都是 0 时，改为每人权重 1，再按同一规则分。个人饼图按类型汇总时，把这次合计分摊拆回各笔，使类型合计与总账一致；这个拆分不返回给客户端。

**Rationale**: 规格要求公共支出合计等于各人承担之和，并且不出现负的承担额。只对前几名做四舍五入时，人数多、金额只有几分，前几名可能把总额分超，最后一名会变成负数。先封顶再把剩余给最后一名，100 元三人平摊仍是 33.33、33.33、33.34。逐笔各自四舍五入再相加会让这个差额随笔数变大，所以总账只用加总后的一次分摊。

**Alternatives considered**:

- 最大余额法：和规格写的「除最后一名外四舍五入」不是同一条规则。
- 允许最后一名为负、再在别人身上扣回：使用者会看到负的承担额。

## 5. 多种转账都合法时选哪一组

**Decision**: 净额先算成「分」。净额大于 0 的人是收款人，小于 0 的是付款人。两组都按当前成员的 id 升序排列，已经不在账本里的人排在当前成员之后，再按姓名、再按 id。按这个顺序，让每个付款人依次把钱付给还没收齐的收款人，直到自己的应付清零。金额为 0 的转账不出现。

**Rationale**: 规格只要求净额结清、笔数不超过人数减 1、同一人不同时收付。规格里的验收例子在这个规则下只有一组结果。把匹配顺序写死，是为了同一次数据不会今天显示甲付给乙、明天显示甲付给丙。

**Alternatives considered**:

- 任意一组合法转账都算通过：手工验收时同一笔账可能对上不同文案。
- 列出每一对成员扣净额之前的毛欠款：规格已经否决，两人页面今天就是一句「谁转给谁」。

## 6. 有效收入和报销

**Decision**: 有效收入只统计收支类型为收入、且归属人就是该成员的金额，再减去已启用规则。归属为「全部」的收入不加给任何人。数量规则只扣浏览器指定的那一名当前成员，扣减额为数量乘以账本中的单价，再四舍五入到分。指定支出类型规则只扣归属人就是该成员的该类支出，不扣已经按公共支出分到他头上的部分。报销进度不参与过滤，也不改金额。支出类型为「基金」的支出参与分账；总消费仍由现有汇总里的总支出减总投资得到，结算接口不重算这三个总数。

**Rationale**: 与规格和澄清一致，也和今天「社保只扣记在这个人名下的支出」一致。报销若在结算里被扣掉，两人账本里已报销的公共账会和现在的应退对不上。

**Alternatives considered**:

- 已报销不参与分账：澄清时已否决。
- 公共支出里的「社保」再按比例从每个人收入里扣一次：会和「只扣归属人就是该成员的支出」重复。

## 7. 已离开的人

**Decision**: 公共支出只在当前成员之间分。归属人不是当前成员、也不是「全部」的支出，全额由这笔账上的归属人承担；记账人不是当前成员时，垫付仍算在这个记账人上。这两类人出现在转账建议里，使用记账上保存的姓名，不画个人支出结构。当前成员不足两人、且所有净额都是 0 时，文案为「无需分账」。只要有非零净额，就列出转账，即使当前只剩一名成员。

**Rationale**: 规格要求不要把已离开的人的账摊给在场的人，同时也要求一名成员、没有别人可结时不要编造转账对象。两种情况用「有没有非零净额」分开。

**Alternatives considered**:

- 一名成员时一律写「无需分账」，即使他还垫付了已离开的人的钱：这笔钱会在建议里消失。
- 为已离开的人画饼图：规格只要求当前成员各有一张。

## 8. 两人文案与多人列表

**Decision**: 结算结果带上已经写好的文案行，电脑端原样显示。恰好两名当前成员、且没有已离开的人参与时：没有转账用「双方结清，无需转账」，有转账用一行「甲 → 乙 转 N 元」。三名及以上，或有已离开的人参与时：没有转账用「各方结清，无需转账」，否则逐行列出。一名当前成员且净额都是 0：一行「无需分账」。

**Rationale**: 两人家庭看的仍是今天这一句。文案放在服务端，是为了验收时不会在浏览器里再算一遍方向。

**Alternatives considered**:

- 浏览器自己拼句子：两人、多人和「无需分账」的分支会和净额各写一处。

## 9. 个人支出结构怎么排

**Decision**: 一名成员时只保留「全部」。两名及以上时，「全部」加上每一名当前成员各一张，按成员 id 升序排在「全部」之后。饼图区域用三列网格，放在 `el-scrollbar` 里，不限制总高度。点「全部」或某一成员时，明细都只显示记账金额，列名为「金额」。点某一成员时，只含归属该成员的记录和归属「全部」的记录。结算接口不返回逐笔份额。

**Rationale**: 分账后的金额和记账金额并排时，明细和总账容易对不上，也不是查看流水所需要的。个人饼图已经表达每人分到的类型合计。

**Alternatives considered**:

- 继续按 32% 宽排三张：第四个人会被挤出或缩没。
- 只显示前两名的图：这就是本次要去掉的行为。
