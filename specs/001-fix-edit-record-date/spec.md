# Feature Specification: 小程序编辑记账回填原日期

**Feature Branch**: `001-fix-edit-record-date`

**Created**: 2026-10-08

**Status**: Draft

**Input**: User description: "小程序编辑记录时，没有回填日期，而是把当前日期填上去了，修复一下"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 编辑时看到这笔账原来的日期 (Priority: P1)

记账人在微信小程序里打开自己早先记的一笔账要修改时，日期一上来就应是这笔账保存下来的那个自然日，而不是打开页面这一天。从账本流水进去和从搜索结果进去，都应如此。

**Why this priority**: 日期被填成今天后，用户往往只改金额或备注就保存，历史账会被挪到今天，当日合计和以后对账都会错。这是本次要修的问题。

**Independent Test**: 准备一笔日期不是今天、且记账人是当前用户的收支。在小程序从流水和从搜索分别打开编辑，日期都显示该笔原日期。

**Acceptance Scenarios**:

1. **Given** 一笔本人记账的日期是过去某一天，**When** 从账本流水打开编辑，**Then** 日期显示该笔原日期，不是今天。
2. **Given** 同一笔非今日记账，**When** 从搜索结果打开编辑，**Then** 日期同样显示该笔原日期。
3. **Given** 一笔跨月或跨年的历史记账，**When** 打开编辑，**Then** 年、月、日都与这笔账在流水里展示的日期一致。
4. **Given** 一笔日期就是今天的本人记账，**When** 打开编辑，**Then** 日期显示今天，与原日期一致。
5. **Given** 修复已经交给使用者，**When** 查看用户手册里关于小程序编辑记账的说明，**Then** 能读到：日期一开始就是这笔账原来的日期，不是打开页面的当天。

---

### User Story 2 - 不改日期保存仍留在原来的那一天 (Priority: P1)

用户打开编辑后没有动日期就保存，这笔账必须仍归在原来的自然日。只有用户自己把日期改成另一天并保存，日期才改变。

**Why this priority**: 回填若只改了眼前的显示、保存时仍写成今天，问题依然在。用户要能放心只改别的内容。

**Independent Test**: 编辑一笔非今日记录，不碰日期，只改金额或内容后保存；流水里该笔仍在原日期分组下。再另开一笔，把日期改成另一天后保存，确认只改到新的那一天。

**Acceptance Scenarios**:

1. **Given** 编辑页已显示原日期，**When** 不修改日期、只改金额或内容后保存，**Then** 该笔记账仍在原来的自然日，原日与今日的收支合计不因这次保存串日。
2. **Given** 编辑页已显示原日期，**When** 不改任何内容直接保存，**Then** 日期保持不变。
3. **Given** 编辑页已显示原日期，**When** 用户把日期改成另一天并保存，**Then** 该笔改到新日期，金额、类型、归属人、内容等未改字段保持原值。
4. **Given** 用户已打开编辑但尚未保存，**When** 离开编辑页，**Then** 原记账日期不变。

---

### User Story 3 - 新增记账仍默认今天 (Priority: P2)

在小程序新记一笔时，日期仍然默认是打开录入页的当天。用户可以改成别的日子再保存。

**Why this priority**: 这次只修「编辑已有记录」的回填。日常补记默认今天是正在使用的习惯，不能被这次修复带偏。

**Independent Test**: 打开小程序新增记账，日期为今天；改成另一天后保存，该笔归在所选那一天。

**Acceptance Scenarios**:

1. **Given** 用户要新记一笔，**When** 打开录入页，**Then** 日期默认为今天。
2. **Given** 新增页日期默认为今天，**When** 用户改成另一天并保存，**Then** 该笔归在用户选择的那一天。

---

### Edge Cases

- 原日期就是今天：编辑页显示今天，不改就保存后仍是今天。
- 原日期为上个月、去年或更早：编辑页显示该历史日期，不改就保存后仍在那天。
- 同一天有多笔：只影响当前正在编辑的那一笔，其它笔的日期不变。
- 不是这笔账的记账人：仍然不能编辑，也不能借编辑把日期改掉。
- 保存没有成功：原记账仍留在原来的自然日。
- 这笔账在流水里能看到明确日期：编辑页必须用这个日期，不得用今天代替。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 在微信小程序编辑已有记账时，系统必须把日期填成该笔已保存的自然日，且在用户可以操作编辑页时就已经是这个日期。
- **FR-002**: 从账本流水进入编辑，和从搜索结果进入编辑，日期回填规则必须相同。
- **FR-003**: 用户未修改日期就保存时，该笔记账的自然日必须保持不变，不得改成打开编辑页的当天。
- **FR-004**: 用户主动把日期改成另一天并成功保存后，该笔记账必须归到新的自然日。
- **FR-005**: 用户打开编辑后未保存就离开，原记账的日期不得改变。
- **FR-006**: 保存未成功时，原记账的日期不得改变。
- **FR-007**: 小程序新增记账时，日期默认仍为打开录入页的当天；用户改过的日期按用户的选择保存。
- **FR-008**: 编辑时，金额、收支（支出或收入）、分类、归属人、内容等其它已有内容必须继续显示为原值；未改动的这些内容在保存后保持原值。
- **FR-009**: 只有该笔记账的记账人可以编辑。不是记账人的成员不能通过编辑修改日期。记账人本身仍不可改。
- **FR-010**: 电脑网页端和手机网页端上，记账的新增、编辑、查询日期行为保持不变。
- **FR-011**: 用户手册中须用一句用户能看懂的话写明：小程序编辑自己的记账时，日期一开始就是这笔账原来的日期，不是打开页面的当天。不借此补写整章小程序指南。

### Key Entities

- **记账明细**：一笔收入或支出。与本次有关的是它的自然日日期，以及金额、收支类型、分类、归属人、内容、记账人。日期按自然日理解，同一天的多笔在流水里归在同一天。
- **编辑表单**：打开某一笔本人记账时，展示这笔账现有的各项内容，供修改后保存。日期是其中一项，打开时必须是这笔账的原日期。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 抽查至少 10 笔日期不是今天的本人记账（其中至少包含 1 笔跨月、1 笔跨年），从流水和从搜索打开编辑后，日期与流水中该笔日期一致的比例为 100%。
- **SC-002**: 上述记录中任选至少 5 笔，不修改日期就保存后，100% 仍留在原来的自然日；原日与今日的笔数、收支合计不因这次保存发生串日。
- **SC-003**: 把其中至少 1 笔的日期改成另一个自然日并保存后，该笔出现在新日期下，原日期下不再有这一笔。
- **SC-004**: 打开新增记账时，日期为当天；不改日期保存则归在当天，改日期保存则归在所选那一天。
- **SC-005**: 不是记账人的成员仍然无法编辑该笔记账。
- **SC-006**: 用户手册中能找到一句说明：小程序编辑自己的记账时，日期显示这笔账原来的日期，不是打开页面的当天。

## Assumptions

- 本次只纠正微信小程序里「编辑已有记账」时日期被填成今天的问题。电脑网页端、手机网页端不在本次范围。
- 「日期」指记账明细上的那个自然日，不是搜索筛选里的开始日或结束日，也不是预算、计划上的日期。
- 正常记账都有一个可在流水里看出来的自然日。编辑回填的就是这个日期。
- 新增记账默认今天、只有记账人本人可编辑或删除、归属人与记账人的区别，都保持现有规则。
- 用户手册目前没有单独的小程序编辑章节。本次只补充 FR-011 那一句，不扩写成完整的小程序使用指南。
- 不改变多人账本隔离、分享加入、报销进度在各端的现有差异。
