# 任务列表：[功能名称]

**输入**: `/specs/[###-feature-name]/` 下的设计文档

**前置条件**: plan.md（必须）、spec.md（用户故事必须）、research.md、data-model.md、contracts/

**测试**: 下列示例含测试任务。测试为**可选**——仅当功能规格明确要求时才写入。

**组织方式**: 按用户故事分组，以便每个故事可独立实现与测试。

## 格式：`[ID] [P?] [Story] 描述`

- **[P]**: 可并行（不同文件、无依赖）
- **[Story]**: 所属用户故事（如 US1、US2、US3）
- 描述中须含确切文件路径

## 路径约定

- **单项目**: 仓库根下 `src/`、`tests/`
- **Web 应用**: `backend/src/`、`frontend/src/`
- **移动端**: `api/src/`、`ios/src/` 或 `android/src/`
- 下列路径按单项目示意——请按 plan.md 结构调整

## 依赖与执行顺序

### 阶段依赖

- **准备（阶段 1）**: 无依赖，可立即开始
- **基础能力（阶段 2）**: 依赖准备完成——**阻塞**全部用户故事
- **用户故事（阶段 3+）**: 均依赖基础能力完成
  - 人力足够时可并行
  - 或按优先级串行（P1 → P2 → P3）
- **打磨（最后阶段）**: 依赖所需用户故事均已完成

### 用户故事依赖

- **用户故事 1（P1）**: 基础能力完成后即可开始——不依赖其他故事
- **用户故事 2（P2）**: 基础能力完成后即可开始——可与 US1 集成，但须可独立测试
- **用户故事 3（P3）**: 基础能力完成后即可开始——可与 US1/US2 集成，但须可独立测试

### 每个用户故事内部

- 若含测试：须先写测试并确认失败，再实现
- 先模型后服务
- 先服务后接口
- 先核心实现后集成
- 本故事完成后再进入下一优先级

### 并行机会

- 准备阶段标 [P] 的任务可并行
- 基础能力阶段内标 [P] 的任务可并行
- 基础能力完成后，各用户故事可并行（视人力）
- 同一故事内标 [P] 的测试可并行
- 同一故事内标 [P] 的模型可并行
- 不同成员可并行推进不同用户故事

## 实施策略

### 先做 MVP（仅用户故事 1）

1. 完成阶段 1：准备
2. 完成阶段 2：基础能力（关键——阻塞全部故事）
3. 完成阶段 3：用户故事 1
4. **停下来验收**：独立测试用户故事 1
5. 若就绪则部署/演示

### 增量交付

1. 完成准备 + 基础能力 → 基础就绪
2. 加入用户故事 1 → 独立验收 → 部署/演示（MVP）
3. 加入用户故事 2 → 独立验收 → 部署/演示
4. 加入用户故事 3 → 独立验收 → 部署/演示
5. 每个故事增量价值，且不破坏既有故事

### 多人并行策略

多人协作时：

1. 团队共同完成准备 + 基础能力
2. 基础能力完成后：
   - 开发者 A：用户故事 1
   - 开发者 B：用户故事 2
   - 开发者 C：用户故事 3
3. 各故事独立完成并集成

## 备注

- [P] 任务 = 不同文件、无依赖
- [Story] 标签将任务映射到具体用户故事，便于追溯
- 每个用户故事应可独立完成与测试
- 实现前确认测试会失败（若有测试）
- 每完成一个任务或逻辑组即提交
- 可在任一检查点停下独立验收故事
- 避免：含糊任务、同文件冲突、破坏独立性的跨故事强耦合
