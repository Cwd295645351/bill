# Research: 支出归属人支持多选

## 1. 多名归属人存在哪里

**Decision**: 不新建表，直接加宽 `transactions` 的两个原有字段，线上用 SQL 脚本升级：

- `belong_user_id`：`VARCHAR(36)` 改为 `VARCHAR(1024)`。多人归属时存按成员顺序、用英文逗号拼接的用户 id，例如 `id甲,id乙`。
- `belong_user_name`：`VARCHAR(64)` 改为 `VARCHAR(2048)`。多人归属时存用「、」拼接的名字，例如 `甲、乙`。

单人归属、「全部」归属的写法和今天完全相同。判断规则只有一条：`belong_user_id` 含逗号就是多人。线上升级脚本和回滚脚本放在 `deploy/sql/`，内容见 [data-model.md](./data-model.md)。

**Rationale**:

- 用户要求直接改原表字段，不新建表。名单和名字都在同一行里，列表、导出、汇总、结算读一次主表就够，不需要额外查询或回填。
- 本仓库靠启动时的 `sequelize.sync()`（不带 `alter`）维护表结构，它不会改已有表的列长度。所以模型里的长度要同步改（新装的库直接建宽列），已有的线上库必须先手工执行升级 SQL，再发布新代码。
- 多人和「全部」一眼就能区分开。今天全仓库都用「`belong_user_id` 为空」判断「全部」：服务端 `isPublicBelong`、电脑端概览明细的前端过滤、小程序卡片底色、手机网页都是这样。逗号串不是空串，漏改的地方最多把它当成一个不认识的人，结果是明显错误，不会悄悄按全员比例分钱。
- 电脑端概览点开某成员的类型明细时，按「该成员或『全部』」查询（本次改为 `belongUserIds = [成员, '']`）。多人行不是空串，不会被「全部」这个条件误带出来。
- 名字直接存在 `belong_user_name` 里，没升级的手机网页不改代码也能看到「甲、乙」。
- 1024 字符能放下 27 个 UUID（36 字符加 1 个逗号）。名字字段按每人最多 64 字加 1 个分隔符计算，2048 足够放下同样人数。超出时服务端拒绝，提示「归属人过多」。家庭账本实际用不到这个上限。

**Alternatives considered**:

- 新建表 `transaction_belong_users`：用户已否决。
- 主表新增一列 `belong_user_ids`：同样要写升级 SQL，而且要维护两列的一致性；原字段加宽后，单人、多人、全部共用一列，口径更简单。
- 多人行 `belong_user_id` 写空串：上面列出的「被悄悄当成全部」风险太大。
- 存 JSON 数组：按成员筛选要用 `JSON_CONTAINS`，依赖 MySQL 5.7+ 的 JSON 支持；逗号串配合 `FIND_IN_SET` 在任何版本都能用，而且单人、多人可以用同一个条件查。

## 2. 名单的顺序

**Decision**: 名单按 `bill_users.id` 升序排列后再拼接写入。展示拼接、分账时的「最后一名」都用这个顺序，与 003 结算接口的成员顺序一致。不修改账本详情 `users` 的返回顺序。

**Rationale**: 规格要求「按账本成员顺序」。003 已经说明 `findBillById` 查成员时没有 `ORDER BY`，返回顺序不能当合同，结算因此固定用 `bill_users.id` 升序。多人归属沿用同一顺序，分账的零头才稳定落在同一个人身上。

**Alternatives considered**:

- 按用户勾选的先后：同一组人勾的先后不同，零头会换人，同一组合也无法合并汇总。
- 改账本详情的成员顺序：会改动记账页和概览下拉的显示顺序，超出本次范围。

## 3. 接口怎么传多名归属人

**Decision**: 接口上用 `belongUserIds: string[]` 替换 `belongUserId`，旧字段从记账相关的请求和响应中移除：

- 新增、编辑、批量新增：`belongUserIds` 必填。请求里只有 `belongUserId`、没有 `belongUserIds` 时，拒绝并提示「当前版本过旧，请更新后再记账」。
- 列表、导出的筛选条件改为 `belongUserIds`。
- 列表 `datas[]` 和汇总 `belongUserCosts[]` 只返回 `belongUserIds`，由数据库 `belong_user_id` 按逗号拆出：「全部」为 `[]`，单人为 `[id]`，多人为按成员顺序的名单。
- 数据库列名 `belong_user_id` 和 Sequelize 属性名不变，只在接口层换成新字段。
- 结算请求的 `quantityInputs[].belongUserId` 表示「数量规则扣到谁」，不是记账的归属人，保留不变。

逐端字段对照见 [contracts/transaction-belong-users.md](./contracts/transaction-belong-users.md)。

**Rationale**:

- 用户决定：有了新字段后，旧字段不再保留。同时保留两个字段，就要长期维护「两者冲突时以谁为准」「只传一个时怎么推断」这些规则，客户端也会继续混用。
- 旧客户端（没更新的小程序、手机网页）只会发 `belongUserId`。如果服务端把缺失的 `belongUserIds` 当成空名单，单人支出会被悄悄存成「全部」，导致分账错误而且不易发现。所以写入接口要识别出旧请求并明确拒绝。
- 查询接口不会写坏数据，旧请求只是丢掉了归属人筛选条件，不报错。
- 这是宪章原则 IV 意义上的破坏性变更，在 [plan.md](./plan.md) 的 Complexity Tracking 中登记了理由。

**Alternatives considered**:

- 新增 `belongUserIds`，同时保留 `belongUserId`：用户已否决。
- 把 `belongUserId` 改成可以接收数组：字段名还是单数，含义含糊，旧客户端照样会传字符串。
- 缺少 `belongUserIds` 时按空名单处理：旧版本小程序记的单人支出会被存成「全部」。

## 4. 保存时的校验

**Decision**: 校验统一放在服务端 `server/database/services/belongUsers.js`，新增、编辑、批量新增都调用它：

1. 名单去重前后长度不同时拒绝，提示「归属人不能重复」。
2. 名单中有人不在 `bill_users` 里时拒绝，提示「归属人不是该账本成员」。
3. 收入：名单必须恰好 1 人，否则拒绝，提示「收入只能选一名归属人」。
4. 支出：0 人按「全部」，1 人按单人，2 人及以上按多人。
5. 拼接后的 id 串超过 1024 字符或名字串超过 2048 字符时拒绝，提示「归属人过多」。

**Rationale**: 规格 FR-002、FR-003、FR-014 都要求服务端拒绝，界面限制只是第一道。今天的新增、编辑在归属人不是成员时会因为读到 `undefined.id` 直接抛错，这次一并改成明确的提示。识别旧请求（第 3 节）放在这些校验之前。

**Alternatives considered**:

- 只在界面上限制：手机网页和旧版本小程序仍能写入归属「全部」的收入。

## 5. 按成员筛选怎么找到多人归属

**Decision**: `buildFilter` 和导出改为读取请求里的 `belongUserIds`，不再直接写 `belongUserId IN (...)`，改由 `belongUsers.js` 生成一组 `OR` 条件：

- 筛选值里的每个成员 id 生成 `FIND_IN_SET(成员 id, belong_user_id) > 0`。单人行等于这个 id，多人行的逗号串里包含这个 id，两种都能命中。
- 筛选值里的空串生成 `belong_user_id = ''`，表示「全部」。
- 筛选值为空（界面上的「全部」）时不加任何归属人条件，两端都是不限归属人。

条件用 `sequelize.where(sequelize.fn('FIND_IN_SET', id, sequelize.col('belong_user_id')), Op.gt, 0)` 生成，成员 id 走参数绑定，不手工拼 SQL。

**Rationale**: `FIND_IN_SET` 按逗号分隔做完整元素匹配，不会把一个 id 当成另一个 id 的子串误命中，也不依赖 MySQL 的 JSON 支持。电脑端搜索、小程序搜索、导出、概览类型明细都走同一个函数，口径不会分叉，满足 FR-012。`belong_user_id` 今天没有索引，按归属人筛选本来就是在日期、账本条件之后过滤，性能特征不变。

**Alternatives considered**:

- `LIKE '%id%'`：需要处理首尾逗号，写法容易出错。
- 在主表用 `LIKE` 匹配拼接的名字：改名或重名都会误判。

## 6. 多人归属支出怎么分账

**Decision**: 在 `overviewSettlement.js` 里给多人归属单独走一条路径：

1. 按 `belong_user_id` 的逗号串把区间内的多人归属支出分组。逗号串保存时已按成员顺序排好，可以直接作为分组键。不同付款人的同组记账放在同一组。
2. 每组先汇总金额，再用组内成员的权重分一次：权重是各人的有效收入，小于 0 按 0；组内权重全为 0 时每人权重 1。分配函数复用现有 `allocatePublic`：按成员顺序除最后一名外四舍五入，最后一名拿剩余。
3. 支出结构按类型拆开时，沿用「全部」的做法：先逐笔分，再用 `reconcileToTarget` 把差额对齐到整组只分一次的结果。
4. 指定支出类型规则：同样按组汇总该类型的金额，再在组内平均扣减，取整规则同上。
5. 名单里如果有人已不在账本：规格明确不考虑这种情况。实现上不报错，也不额外处理：这个人按局外人加入结算，权重为 0。

**Rationale**: 规格 FR-007 要求同组先汇总再分，FR-009 要求指定类型的扣减也一样。「全部」支出今天就是汇总后只分一次再逐笔对齐，多人归属复用同一组函数，零头规则不会出现两套。

**Alternatives considered**:

- 逐笔分完再加总：用户已明确否决。
- 把所有多人组合并成一个池子：「甲、乙」和「甲、丙」权重基数不同，不能合并。

## 7. 汇总接口里的多人归属

**Decision**: `GET /overview/balance` 和 `GET /transaction/currentMonthCost` 的总额不变。它们的 `belongUserCosts` 今天按「归属人 id + 记账人 + 收支类型」分组。多人行的归属人 id 就是逗号串，不同组合自然分开，同一组合自然合并，分组代码不需要改，只在每项上增加 `belongUserIds`。`costTypeRank` 按归属人名字分组，多人行用拼接名，也不需要改。

**Rationale**: 总额是四端都在读的数字，不能动。分组键只影响明细项，旧客户端读到的仍是同样的字段。

**左侧明细**: 电脑端概览左侧从 003 起只显示收入行（`Overview.vue` 里的 `incomeDetails` 会过滤掉支出），收入又不能多人归属，所以左侧不会出现多人归属行。2026-10-13 已澄清不需要多人支出行，规格 US3 场景 7 和 FR-011 已改为保持现状。

## 8. 小程序的交互和「上次归属人」

**Decision**: `record-form` 组件里用平铺标签代替现在的滚轮选择器。支出时显示「全部」和各成员，点一下选中或取消：

- 点「全部」会清掉其他成员；点任一成员会清掉「全部」；全部取消时自动回到「全部」。
- 收入时只显示成员，按单选工作。
- 从支出切换到收入时，名单多于 1 人或是「全部」，就改成自己并弹提示；只有 1 人时保留。

本地缓存 `RecordPref` 改为保存 `belongUserIds` 和 `belongUserName`，不再写 `belongUserId`。读取时，如果缓存里只有旧版本写入的 `belongUserId`，就转成 `[]` 或 `[id]` 使用一次，下次保存时按新格式覆盖。记支出时，默认使用上次的名单。记收入时，上次是单人就用这个人，否则用自己。

**Rationale**: 与 2026-10-13 的澄清一致。本地缓存不经过服务端，更新小程序后第一次打开还会读到旧格式，所以读取时要兼容一次；写入只用新格式。

**Alternatives considered**:

- 弹层勾选后再确认：用户已选择平铺标签。

## 9. 电脑端的选择控件

**Decision**: 电脑端新增、编辑弹窗里的归属人改成 `el-select multiple`。支出时，「全部」与成员互斥的逻辑写在一个共用的 hook 里；收入时用单选，不放「全部」选项。批量解析表格的归属人仍是单选，不在本次范围。时间线卡片对多人归属使用一种固定底色 `#ede7f6`（淡紫），不在现有 8 色调色板里，与白底也能区分。小程序流水使用同一颜色。

**Rationale**: Element Plus 的 `multiple` 已在项目依赖里，不新增组件。固定底色是规格边界情况里的要求。

**Alternatives considered**:

- 复选框组：成员多时会占用表单很多宽度。

## 10. 测试方式

**Decision**: 不引入测试框架。分账是纯函数，[quickstart.md](./quickstart.md) 给出用 `node -e` 直接调用 `buildSettlement` 核对规格 US2 八个例子的方法，其余按页面手工验收。

**Rationale**: 与 003 一致：`server` 的 test 脚本仍是占位，宪章原则 I 不允许为了填模板编造覆盖率标准。

**Alternatives considered**:

- 本次顺带引入 Jest：不属于本功能，违反「禁止顺便重构」。

## 11. 线上升级怎么执行

**Decision**: 新增 `deploy/sql/004-multi-belong-users-upgrade.sql` 和 `deploy/sql/004-multi-belong-users-rollback.sql`，并在 `deploy/README.md` 增加「数据库升级脚本」一节，写明执行顺序：

1. 备份 `transactions` 表。
2. 执行升级脚本：只加宽两列，不改数据。
3. 发布新版服务端和电脑端，再立即提交小程序新版本审核并发布（规格 FR-022）。

升级脚本先发布、旧代码照常运行：加宽列不影响旧代码读写。反过来，如果先发布新代码、没执行脚本，写入多人归属时会因为超出列长度失败。所以顺序必须是先脚本、后代码。

`server/database/models/index.js` 里两列的长度同步改成 1024 和 2048，新装的环境由 `sequelize.sync()` 直接建出宽列，不需要执行脚本。脚本可以重复执行（`MODIFY COLUMN` 改成相同定义没有副作用）。

**Rationale**: 线上库已有数据，`sync()` 不改已有列，只能手工升级。脚本只加宽、不迁移数据，是可逆的最小变更，满足宪章原则 IV「数据库变更必须可回滚」。

**Alternatives considered**:

- 启动时自动执行 `ALTER`：服务端需要 DDL 权限，而且多实例同时启动可能重复执行，不如由运维显式执行。
- `sequelize.sync({ alter: true })`：会按模型改动整张表的所有列，影响面不可控。

## 12. 移除旧字段后，旧版本客户端怎么过渡

**Decision**:

1. 小程序在 `app.ts` 里接入 `wx.getUpdateManager()`：检测到新版本下载完成后，弹出不可取消的提示框，用户确认后调用 `applyUpdate()` 重启到新版本。仓库里现在还没有这段逻辑。
2. 服务端写入接口识别旧请求（见第 3 节）并拒绝，提示「当前版本过旧，请更新后再记账」。小程序会原样显示服务端返回的 `message`。
3. 发布顺序：执行升级 SQL → 发布服务端和电脑端 → 立即提交小程序新版本审核并发布。电脑端是浏览器加载的静态页，必须和服务端一起上线，刷新页面就是新版本。
4. 回滚必须成套（规格 FR-022）：小程序新版本发布之前，可以单独回滚服务端和电脑端。发布之后，如果要回滚服务端，必须同时在微信公众平台把小程序回退到旧版本；只回滚服务端时，新版本小程序只发 `belongUserIds`，旧服务端读不到，会把单人支出存成「全部」。
5. 手机网页不改。上线后它的新增和编辑会被拒绝；查看流水还能看到归属人名字（`belongUserName` 保留）；按归属人搜索时条件被忽略，结果等同于不限归属人。

**Rationale**: 小程序发布新版本后，用户要等到下次冷启动才会切到新版本。从服务端上线到小程序审核通过，中间有一段时间旧版本还在用。强制更新能缩短这段时间；明确拒绝能保证这段时间里不会写进错误数据。手机网页受影响的范围已经被规格 FR-018 接受（不作保证，后续下线）。

**Alternatives considered**:

- 保留一个版本的兼容期，期间继续读 `belongUserId`：用户已决定移除旧字段。如果小程序审核时间长，这是可以退回的方案。
- 先发布小程序、后发布服务端：新版本小程序发的 `belongUserIds` 在旧服务端上会被忽略，多人支出会被存成「全部」，问题更严重。
