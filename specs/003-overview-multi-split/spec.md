# Feature Specification: 概览统计支持多人分账

**Feature Branch**: `003-overview-multi-split`

**Created**: 2026-10-12

**Status**: Draft

**Input**: User description: "概览统计需要支持多人分账"

## Clarifications

### Session 2026-10-12

- Q: 记了报销进度的支出，分账时是按记账金额全额计算，还是把某些报销状态排除在外？ → A: 不论报销进度，都按记账金额全额参与分账

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 三名及以上成员能按全体分摊并知道该转给谁 (Priority: P1)

一个账本里不只有两个人。月末或年底，任一成员在电脑上打开概览，选定时间，点查询后，归属为「全部」的公共支出按**全体当前成员**的有效收入比例分摊，不再只按成员列表里的前两名。代付（记账人是付款人、归属人是另一个成员）仍全额算在归属人头上。页面给出一组可以直接照做的转账建议，照做之后每个人不多付、也不少付。

**Why this priority**: 今天三人及以上只能把概览当参考，再手工扣掉第三人。分账若仍忽略后面的成员，这次就没有解决用户要办的事。

**Independent Test**: 建一个三名成员、有效收入相同的账本，只记一笔甲支付的 300 元且归属「全部」。查询后每人承担 100 元，乙、丙各转给甲 100 元（合计 200 元）。甲自己承担的 100 元不再转出。不需要再把第三人的份额手工减掉。

**Acceptance Scenarios**:

1. **Given** 账本成员为甲、乙、丙，三人有效收入相同，区间内只有一笔甲支付的 300 元且归属为「全部」，**When** 在电脑端概览查询该区间，**Then** 每人承担 100 元，结算建议为「乙 → 甲 转 100 元」和「丙 → 甲 转 100 元」，不出现只在甲、乙之间结算 150 元而把丙排除在外的结果。
2. **Given** 同上账本，甲给乙买了 300 元衣服（记账人甲、归属人乙），另有丙支付的 90 元聚餐（归属「全部」），三人有效收入相同，**When** 查询，**Then** 乙承担衣服 300 元再加聚餐中的 30 元，甲、丙各承担聚餐 30 元；结算建议为「乙 → 甲 转 270 元」和「乙 → 丙 转 60 元」。
3. **Given** 四名成员、有效收入相同，其中一人支付 100 元且归属「全部」，**When** 查询，**Then** 四人各承担 25 元，另外三人各自转 25 元给付款人，建议转账不超过 3 笔。
4. **Given** 三名成员的有效收入分别为 6000、3000、3000，甲支付 1200 元且归属「全部」，**When** 查询，**Then** 甲承担 600 元、乙承担 300 元、丙承担 300 元，乙和丙各转 300 元给甲。
5. **Given** 已查出一组结算建议，**When** 用户只改了开始时间、结束时间或数量规则、还没再点「查询」，**Then** 分摊和结算建议仍是上一次的结果；再点「查询」后才按新条件更新。
6. **Given** 用户手册仍写着三人及以上只按前两名计算，**When** 本能力交付，**Then** 手册改为全体当前成员参与分摊和结算，并至少有一个三人例子，读法与页面上的「谁转给谁」一致。

---

### User Story 2 - 两人账本的应退结果和读法保持不变 (Priority: P1)

已经按两人使用概览的家庭，公共吃饭、代付、用规则调整收入之后，应退方向和金额与现在手册中的算法一致。文案仍是「甲 → 乙 转 N 元」，结清时仍是「双方结清，无需转账」。不能因为支持了更多人，就把两人的结果改掉。

**Why this priority**: 两人是现在每天在用的分账。多人分账如果顺带改了两人的转账金额，已经结过的账会对不上。

**Independent Test**: 用手册中的两人例 1（共同吃饭）和例 2（代付）各查一次，应退方向和金额与手册一致；有效收入之和为 0 时仍按 1:1。

**Acceptance Scenarios**:

1. **Given** 成员只有甲、乙，有效收入相同，甲付 200 元且归属「全部」，**When** 查询，**Then** 各承担 100 元，应退为「乙 → 甲 转 100 元」。
2. **Given** 成员只有甲、乙，甲给乙买衣服 300 元（归属人乙），**When** 查询，**Then** 这 300 元全部算乙承担，应退为「乙 → 甲 转 300 元」。
3. **Given** 成员只有甲、乙，甲有效收入 6000、乙 4000，甲付 1000 元且归属「全部」，**When** 查询，**Then** 甲承担 600 元、乙承担 400 元，应退为「乙 → 甲 转 400 元」。
4. **Given** 成员只有甲、乙，两人有效收入都是 0（没有收入，也没有规则扣减），甲付 200 元且归属「全部」，**When** 查询，**Then** 仍按 1:1，乙 → 甲 转 100 元。
5. **Given** 两人按当前规则已经平衡，**When** 查询，**Then** 文案为「双方结清，无需转账」，不出现 0 元转账。
6. **Given** 成员只有甲、乙，甲的归属收入为 8000，数量规则填 10、单价 200 且归属人选甲（扣 2000），乙的归属收入为 10000，另有一笔归属乙的 1000 元被「社保」规则扣掉，甲支付 15000 元且归属「全部」，**When** 查询，**Then** 甲有效收入为 6000、乙为 9000，甲承担 6000 元、乙承担 9000 元，应退为「乙 → 甲 转 9000 元」，而不是按扣减前的收入或按 1:1。
7. **Given** 成员只有甲、乙，有效收入相同，甲付 200 元且归属「全部」，该笔报销进度为「已报销」（待报销、已提交同样适用），**When** 查询，**Then** 仍按记账金额 200 元分摊，应退为「乙 → 甲 转 100 元」，与「无需报销」时相同。

### User Story 3 - 每人都能看到自己该承担的支出结构 (Priority: P2)

查询之后，除了未拆分的「全部」支出结构，每一名成员都有自己的支出结构：里面是归属自己的支出，加上自己分到的公共支出，没有归属别人的那部分。点开某一类时，明细只显示记账金额。只有一名成员时，仍然只看「全部」。

**Why this priority**: 转账建议回答「转多少」，支出结构回答「钱花在哪」。没有个人结构，多人只能看到一个总数，对不上自己的份额。它依赖分摊比例已经按全体成员算对，所以排在结算之后。

**Independent Test**: 三名成员、一笔公共餐饮和一笔只归属乙的购物。全部结构里两类都在；乙的结构里两类都在且餐饮只占其份额；甲和丙的结构里有餐饮份额、没有那笔购物。只有一名成员时仍然只有一张「全部」。

**Acceptance Scenarios**:

1. **Given** 账本至少有两名成员，**When** 查询概览，**Then** 能看到未按人拆分的「全部」支出结构，以及每一名当前成员各自的支出结构，不能只画出前两名。
2. **Given** 有一笔归属乙的购物，和一笔归属「全部」的餐饮，**When** 查看乙的支出结构，**Then** 两类都在，餐饮金额是乙分到的份额；查看甲的支出结构时，有餐饮份额，没有这笔购物。
3. **Given** 用户点开某一成员结构中的某一类，**When** 查看明细，**Then** 金额列只显示记账金额，不显示分账后的金额。归属其他成员的记录不出现在这里。
4. **Given** 用户点开「全部」结构中的某一类，**When** 查看明细，**Then** 金额不按人拆开，仍是每笔记账的原金额。
5. **Given** 账本只有一名成员，**When** 查询，**Then** 仍然只显示「全部」支出结构，并说明无需分账，不出现转账对象。

---

### Edge Cases

- 公共支出先把区间内归属为「全部」的金额加总，再只分一次。不能被人数整除时（例如合计 100 元、三人、有效收入相同），按成员列表现有顺序，先到的人四舍五入到分，最后一名承担剩余差额，三人合计必须仍是 100 元。多笔都除不尽时，不以逐笔四舍五入后再相加的结果作为总账。
- 全体成员有效收入按规则折算后都是 0：在当前成员间均分。两人时就是现在的 1:1。
- 某成员有效收入为负：该成员分摊比例按 0 计，不出现负的承担额。若因此所有人比例都是 0，则改为均分。
- 某成员本期没有收入也没有记账，但其他人有公共支出：仍参与分摊。其他人有效收入为正时，此人比例为 0，不承担公共支出；全体有效收入都为 0 时，此人与其他人平摊。
- 记账人与归属人是同一人：这笔在净额里抵消，不产生「自己转给自己」。
- 区间内没有任何支出：每个人净额为 0。两人显示「双方结清，无需转账」；三人及以上显示「各方结清，无需转账」。
- 算出的某笔转账不足 1 分：不列出这笔，视作结清。
- 数量规则只扣被选中的那一名归属人，不按人数复制一份数量。指定支出类型规则只扣「归属人就是该成员」的该类支出，不把已经归属「全部」、再分摊到个人的金额再扣一次。
- 归属为「全部」的收入不拆进任何成员的有效收入。收入金额本身不参与「谁垫付了谁」的净额，只通过有效收入影响公共支出比例。
- 某笔支出的归属人或记账人已经不在当前成员列表中，且归属人不是「全部」：不把这笔摊给在场的其他人。结算里保留这个名字，由该归属人承担；若记账人不是该归属人，则归属人应付给这名记账人。归属为「全部」的支出只在当前成员之间分。
- 成员很多时，仍然要能逐一看到每个人的支出结构和全部结算建议，不能只保留前两名。
- 总支出、总投资、总消费、总收入，以及近三年趋势，不因人数变多而改口径。近三年趋势不按人拆开。分账包含区间内全部支出，包括「基金」；报销进度为无需报销、待报销、已提交或已报销时，都按记账金额全额计入。总消费仍然是总支出减去基金，两套数字不要混用。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 电脑端概览必须按当前账本的每一名成员分摊公共支出并给出结算建议。不得只使用成员列表中的前两名。
- **FR-002**: 归属为某一成员的支出，必须全额由该成员承担，与谁记账无关。
- **FR-003**: 归属为「全部」的支出，必须按各成员有效收入比例分摊。比例用的有效收入小于 0 时按 0 计。全体都按 0 计时，在当前成员间均分。
- **FR-004**: 归属为「全部」的公共支出先加总，再按权重只分一次，金额保留到分。按成员列表现有顺序，除最后一名外四舍五入到分，最后一名用总额减去前面各人金额。各人承担的公共部分合计必须等于公共支出总额。不得把逐笔四舍五入的结果相加当作总账。
- **FR-005**: 成员的有效收入等于「归属到该成员的收入」减去已启用的概览规则扣减。数量规则只扣查询时选中的那一名归属人。指定支出类型规则只扣归属人就是该成员的该类支出。归属为「全部」的收入不计入任何成员。
- **FR-006**: 成员净额等于「其作为记账人支付的支出合计」减去「其应承担的支出合计」。收入金额不计入净额。净额为正表示别人应转给该成员，为负表示该成员应转出。
- **FR-007**: 结算建议是一组「付款人 → 收款人 转 N 元」，照做后每位相关人员的净额在分位上归零。建议笔数不超过参与结算的人数减 1。同一人在这组建议里不能既付款又收款。金额保留两位小数。不足 1 分的转账不出现。
- **FR-008**: 恰好两名成员、且双方有效收入都非负时，结算建议至多一条，文案保持「甲 → 乙 转 N 元」。净额为 0 时文案为「双方结清，无需转账」。本规格用户故事 2 的例 1、例 2 和 6000:4000 的公共支出例子，方向和金额必须保持不变。
- **FR-009**: 三名及以上成员时，列出全部建议转账。全部结清时文案为「各方结清，无需转账」。只有一名成员时，说明无需分账，不出现转账对象。
- **FR-010**: 「全部」支出结构必须仍是未按人拆分的整体。账本至少有两名成员时，每一名当前成员都有自己的支出结构，包含归属自己的支出和自己分到的公共支出，不包含归属其他成员的支出。只有一名成员时，仍然只显示「全部」。
- **FR-011**: 从支出结构查看某类明细时，只显示记账金额，列名为「金额」。不展示分账后的金额，结算接口也不返回逐笔份额。从某一成员的结构查看时，只含归属该成员或归属「全部」的记录。从「全部」结构查看时，不按人拆金额。
- **FR-012**: 修改起止时间或数量规则后，必须再次查询，分摊、个人支出结构和结算建议才更新。默认统计区间仍是当年 1 月 1 日至今。
- **FR-013**: 总支出、总投资（支出类型为「基金」）、总消费（总支出减去总投资）、总收入，以及近三年趋势（不含今年、总消费剔除基金）的现有口径必须保持不变。近三年趋势不按成员拆分。
- **FR-014**: 手机网页和小程序不新增这套分账，记账、流水和账本内已有汇总数字保持不变。概览规则仍只有账本创建者可以配置，规则种类和填写方式保持不变。
- **FR-015**: 用户手册必须写明：公共支出和应退按全体当前成员计算，不再只按前两名；两人时的读法不变；并给出至少一个与页面文案一致的三人例子。不借此重写整本手册。
- **FR-016**: 报销进度不改变该笔支出是否参与分账，也不改变计入的金额。无需报销、待报销、已提交、已报销都按记账金额全额计算。分摊、净额和结算建议都使用这个金额。

### Key Entities

- **账本成员**：当前在这个账本里的人。分摊公共支出时以这份名单为准，顺序沿用账本成员的现有顺序。
- **支出明细**：一笔支出，有记账人（谁付的）、归属人（算在谁头上，或「全部」）、金额、支出类型和报销进度。分账使用记账金额，报销进度不减少这笔钱。分账不改变这些明细本身。
- **有效收入**：某一成员在查询区间内、扣掉已启用概览规则之后、用来比分摊比例的收入。不是总收入那个汇总数。
- **应承担金额**：归属该成员的支出，加上其分到的公共支出。
- **结算建议**：一组两人之间的转账，使每个人垫付与应承担的差额结清。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 三名成员、有效收入相同、只有一笔甲支付的 300 元公共支出时，用户点一次查询后，能在同一屏读完「乙 → 甲 转 100 元」和「丙 → 甲 转 100 元」。两笔之和为 200 元，甲自己承担的 100 元不出现在转账里，也无需再手工扣除第三人。
- **SC-002**: 手册两人例 1、例 2，以及「有效收入 6000 与 4000、公共支出 1000」这三组，查询后应退方向和金额与本规格用户故事 2 一致的比例为 100%。
- **SC-003**: 查询区间内归属为「全部」的支出先加总再只分一次。各成员承担的公共部分之和与该总额相差不超过 0.01 元。不能整除时，差额落在成员顺序的最后一名，不因笔数变多而扩大。
- **SC-004**: 至少一组三名成员、净额不全为 0 的查询，结算建议不超过 2 笔，且按建议转完后无人仍应收或应付（误差不超过 0.01 元）。
- **SC-005**: 改了日期或数量但未再查询时，结算建议保持上一次结果；再查询后，用户能在一次查看里读完全部建议转账，而不是只看到前两名之间的一笔。
- **SC-006**: 用户手册中不再出现「三人及以上只按成员列表前两名计算」，并能找到至少一个三人分账例子。

## Assumptions

- 本次只改电脑端概览里的分摊、个人支出结构和结算建议。手机网页和小程序继续不提供这套分账。
- 「多人」指当前账本成员人数可以是 1、2、3 或更多。两人是现有行为的回归，三人及以上是这次要补上的能力。不设人数上限；成员很多时仍须看全每个人，而不是改回前两名。
- 分摊比例沿用现在的含义：有效收入越高，承担的公共支出越多。没有另选「按人头固定比例」或「按消费占比」等其它办法。
- 有效收入为负时按 0 计。手册没有写过负数收入怎么分，这是本次采用的默认。两人且双方都非负时，不因这条默认而改变故事 2 的结果。
- 结算建议采用「转账笔数尽量少、同一人不要又付又收」的列法，因为现在两人页面就是一句「谁转给谁」。不改为列出每一对成员的毛欠款。
- 概览规则的配置方式不变：仍然是数量乘单价，或指定某一支出类型；数量仍是查询时填的一个数，并指定一名归属人。不为每个成员各加一个数量框。
- 左侧按记账人、归属人展开的明细行是否展示支出，不在本次范围内。分账按查询区间内的支出明细计算，不按这些行在屏幕上是否看得见来取舍。
- 总支出、总投资、总消费、总收入、近三年趋势、预算、计划、记账录入、类型管理、分享加入账本，均不改变。分账按区间内全部支出的记账金额计算，包含「基金」，也不因报销进度减少金额；总消费继续单独剔除基金。
- 账本之间仍然隔离。记账人仍然不可修改。归属人仍然是某个成员或「全部」。只有记账人可以改自己录入的明细。这些不变量不被分账绕过。
- 用户手册只改与概览分摊、应退读法和三人及以上相关的段落，并补一个三人例子。不重写其它章节。
