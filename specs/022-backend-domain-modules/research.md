# 研究记录：后端按业务领域重组并补齐账本权限

**功能分支**: `022-backend-domain-modules` | **日期**: 2026-11-17

## 1. 业务代码放在哪里

**决策**: 业务按领域放在 `server/modules/<领域>`。每个领域对外只通过自己的 `index.ts`。路由解析参数并写出响应，服务函数不接收请求上下文、不写响应体。`server/database` 只保留连接、按领域拆开的模型、启动补表，以及新建账本的默认分类名单 `initDatas.ts`。这份名单由账本模块调用，不迁进模块，也不写回 `database/services`。迁完后删除 `server/routes`、`server/database/services`、`server/model`。

**理由**: 现在登录、分账、汇率、照片和整本账加载都堆在 `database/services`，目录名和依赖对不上。规格要求账号、账本、类型与概览规则、预算、计划、记账、概览、资产、智能解析各自成块，账本权限单独一处且没有用户页面。只把控制器挪进 `database/services` 仍会把新代码堆进错误的层。

**备选方案**: 维持 `server/routes` + `server/database/services`。被否决，因为规格明确要求先改宪章落点，再按业务领域组织；维持旧目录无法满足 FR-014。不另做仓储接口或工作单元框架，事务对象仍作为参数传入对方公开函数。

## 2. 宪章何时改

**决策**: 写任何模块代码之前，先把 `.specify/memory/constitution.md` 的「技术栈与模块落点」从「路由在 `server/routes`、业务在 `server/database/services`」改为 `server/modules`。版本 `3.3.0` 升到 `3.4.0`，文首同步影响说明记下这次变化。原则 I 与原则 IV 不改。

**理由**: 现行宪章禁止这套目录。规格 FR-015 规定未修订不得搬迁。先改宪章，后面的代码才不是无记录的违规。

**备选方案**: 先搬代码、最后补宪章。被否决，因为门禁会在实现过程中一直失败，也和规格顺序相反。

## 3. 账本权限只留一处

**决策**: 新增 `server/modules/access`，没有路由。公开 `requireMember(userId, billId)`、`requireCreator(userId, billId)`，以及 `billIdOfAsset`、`billIdOfRecord`、`billIdOfMember`。资产、盘点、资产成员在只有资源编号时先反查账本，再判断是不是账本成员。资产名单 `members` 与账本成员 `bill_users` 继续是两份名单。

判断顺序固定为：先是不是该账本成员，再是不是创建者或记账人。

**理由**: 规格要求成员判断和创建者判断只有一处。现在资产、照片、类型、预算各自查 `bill_users`，文案已经分叉。把实现收拢后，才能按「已有说明保持不变、新补上的用同一句」执行。

**备选方案**: 各模块继续自己查成员表。被否决，因为会留下第二套判断，规格 FR-009 不通过。

## 4. 非成员说明哪些改、哪些不改

**决策**: 凡是针对某一个已有账本的查看或修改，非成员必须失败，且响应里不得带出该账本的明细或金额。新建账本、自己的账本列表、凭有效邀请加入不在此列。

已经会拒绝非成员、并且已有说明的，说明原文保持不变：

| 操作 | 保持的说明 |
|------|------------|
| 预算、计划 | 该用户并未加入此账本 |
| 账本详情 | 找不到账本 |
| 删除账本（非创建者或找不到） | 找不到该账本或您非该账本的创建者 |
| 分账 | 不是该账本成员 |
| 家庭资产 | 无权查看该账本 |
| 类型管理 | 只有账本创建者才能管理类型 |
| 概览规则 | 只有账本创建者才能管理概览规则 |
| 类型里已有的其他拒绝 | 无权访问该账本数据、无权管理该账本数据 |
| 智能解析 | 无权访问该账本 |
| 上传照片时不是成员 | 未找到账本 |
| 签名打开照片失败 | 无权查看 |
| 退出时并未加入 | 您并未加入该账本 |
| 非创建者移除成员 | 仅账本创建者可移除成员 |
| 创建者退出 | 创建者不能退出账本 |

今天只确认登录、本次新补上的拒绝，说明一律为「不是该账本成员」。已核对的缺口至少包括：流水列表、当月支出、导出、导入、新增与批量新增、区间收支、近三年支出。编辑或删除明细时，非成员先得到「不是该账本成员」；已经是成员但不是记账人时，仍分别是「只能编辑自己记的账单」「只能删除自己记的账单」。

修改账本名称：非成员为「不是该账本成员」；是成员但不是创建者时为「只有账本创建者才能修改账本名称」，名称不变。

**理由**: 澄清记录选择了「全部账本操作都拒绝非成员」，同时规格要求不改掉已经在用的失败说明。统一成一句会让预算、资产、详情的现有提示变掉。

**备选方案**: 所有非成员失败都改成「不是该账本成员」。被否决，因为这会改变已经上线的说明，超出「原先已有拒绝说明保持不变」。

## 5. 服务结果如何写成现有响应

**决策**: `server/http/outcome.ts` 表示成功携带数据或失败携带中文说明。`server/http/respond.ts` 把它写成现有响应：成功 `retCode` 为 0，失败 `retCode` 为 1，字段仍是 `retCode`、`message`、`data`。路由不再判断 `[错误, 结果]` 二元组。`server/http/current-user.ts` 只读登录凭证里的 `userId`。响应模型放在 `server/http/res-model.ts`。在旧路由还引用 `server/model/resModel.ts` 时，旧文件只再导出新文件；全部改完后再删除旧文件。

全部模块迁完后，删除 `server/utils/jwtUser.ts`，以及 `app.ts` 里用请求头改写当前用户的那一层。迁完之前旧路由还可以用它，避免半成品无法识别用户。

**理由**: 规格要求身份只认登录凭证，又要求成功字段不增不删。响应组装留在 HTTP 层，服务才能不依赖某一次请求。

**备选方案**: 服务继续返回二元组，由各路由自行组装。被否决，因为九组接口会继续各写一遍，也方便漏掉身份来源。

## 6. 错误的访问方式

**决策**: `app.ts` 挂载每个模块路由时，同时注册路由表和允许的方法。每个模块用自己的允许方法，不再把预算的允许方法套到概览上。用错方法时，调用方能看出是方法不对，而不是没有这个地址。

**理由**: 现在的挂载把允许方法丢掉了，规格 FR-019 要求能区分这两种失败。

**备选方案**: 保持只注册路由表。被否决，因为错误方法仍会表现成地址不存在。

## 7. 表定义如何拆

**决策**: `server/database/models/index.ts` 拆成 `helpers.ts`、`auth.ts`、`bill.ts`、`catalog.ts`、`budget.ts`、`plan.ts`、`transaction.ts`、`asset.ts`，由新的 `models/index.ts` 建立跨表关联并汇总导出。`server/database/index.ts` 继续导出现有模型名字。业务仍从这里导入。不新增表、不加列。`sequelize.sync()` 与 `ensureAssetSchema.ts` 保留。

**理由**: 单文件已经集中约 20 张表，继续追加会把无关表的修改混在一起。导出名单不变，拆文件时旧调用不用先改导入路径。

**备选方案**: 维持单文件，或为每张表加仓储。前者继续混改；后者是规格没有要求的第二套数据访问。

## 8. 记账与预算仍是一次保存

**决策**: 预算模块公开「在给定事务中按现有算法重算并保存」。记账的新增、批量新增、编辑、删除只调用这个函数，不再自己组装预算数组。流水、预算和用户累计收支仍在同一个数据库事务里；失败则整次不留下半截。类型名称仍由类型模块按编号提供，记账沿用现在的快照写法。`findBillById` 这种一次加载类型、预算、计划和成员的整包读取不再对外提供，各领域查自己的表。

**理由**: 规格要求只保留一套预算算法，并要求同一次保存。两套保存逻辑并存会在搬迁中算错当年预算。

**备选方案**: 记账模块复制现有 `saveBudget`。被否决，因为会出现两套算法。

## 9. 负债标记与已完成的加宽脚本

**决策**: 删除无人调用的负债补数文件之前，对目标库执行一次现有补数：类型为负债、仍在使用、但未标成负债的资产标成负债。入口是现有 `server/database/services/runDebtBackfill.ts`（在 `server` 目录执行 `pnpm exec tsx database/services/runDebtBackfill.ts`）。补完后删除 `assetDebtBackfill.ts` 与 `runDebtBackfill.ts`。创建和编辑资产时已经按类型写入该标记，启动和接口都不调用这两个文件。

归属人列加宽已经在线上完成且不再回滚。删除 `deploy/sql`，并从 `deploy/README.md` 去掉目录表里的 `sql/` 行和「数据库升级脚本」整节。`specs/004-multi-belong-users/` 不改。全新空库仍由模型建出宽列。

**理由**: 规格要求补齐负债口径后再去掉死步骤，并要求部署说明不再指向已完成的升级。本次不改表结构。

**备选方案**: 把补数留在启动流程里。被否决，因为启动和接口都不会、也不应该每次扫描全表。保留 SQL 目录也会让发布人员再次执行已完成的加宽。

## 10. 怎么验收

**决策**: 不新增测试框架。每步结束在 `server` 目录执行 `pnpm typecheck`。全部完成后按 `quickstart.md` 做手工回归，并核对用户手册第 14 节：管理类型改为仅创建者，与第 5.4 节一致。电脑网页、手机网页、小程序源码不改。

**理由**: 仓库没有可运行的测试脚本。规格把类型检查和所列场景定为本次完成标准。

**备选方案**: 为本期引入自动化测试框架。被否决，规格 FR-018 明确不做。
