# Quickstart: 支出归属人支持多选

用这份指南验收 [spec.md](./spec.md)。接口以 [contracts/transaction-belong-users.md](./contracts/transaction-belong-users.md) 为准，字段改动、升级和回滚脚本以 [data-model.md](./data-model.md) 为准。这里不写实现代码。

## 准备

1. 数据库升级：对已有数据的本地库，先执行 `deploy/sql/004-multi-belong-users-upgrade.sql`，再用 [data-model.md](./data-model.md) 第 5 节的核对 SQL 确认两列长度为 1024、2048。全新的空库可以跳过这一步，`sequelize.sync()` 会按模型直接建出宽列。
2. 启动服务端：`cd server && npm run dev`。不需要新的环境变量。
3. 启动电脑端：`cd frontend && npm run dev`。
4. 小程序：用微信开发者工具打开 `miniapp/`，「工具 → 构建 npm」后编译。
5. 准备一个三人账本，成员为甲、乙、丙。记下三人在 `bill_users` 中的 `id` 升序，后面「最后一名」按这个顺序判断，下文假设顺序就是甲、乙、丙。
6. 概览验收前，把查询区间收窄到只包含当次记的账。

## 1. 分账纯函数核对（不需要页面）

`server/database/services/overviewSettlement.js` 是纯函数，可以直接在 `server/` 目录下调用：

```bash
node -e "const { buildSettlement } = require('./database/services/overviewSettlement'); console.log(JSON.stringify(buildSettlement(require('./tmp-case.json')), null, 2))"
```

`tmp-case.json` 按 `buildSettlement` 的入参准备：`members`（甲、乙、丙）、`rules`、`quantityInputs`、`transactions`。这是服务端内部的入参，不是接口：多人归属的记账带 `belongUserIds`（例如 `["id甲", "id乙"]`），字段名以实现时 `buildSettlement` 的 JSDoc 为准。用完删掉这个文件，不要提交。

逐一核对规格 US2 的 8 个例子，看 `members[].borne`、`members[].net` 和 `lines`：

| 例子 | 关键预期 |
|------|----------|
| 1 | 甲付 200、归属甲乙：甲、乙各承担 100，`lines` 为「乙 → 甲 转 100.00 元」 |
| 2 | 收入 6000/3000/9000，丙付 900、归属甲乙：甲 600、乙 300、丙 0 |
| 3 | 甲、乙有效收入都为 0，甲付 300、归属甲乙：各 150，丙 0 |
| 4 | 甲付 300 全部 + 乙付 200 归属甲乙 + 丙付 90 归属乙：承担 200 / 290 / 100，净额 +100 / −90 / −10 |
| 5 | 甲付 300、归属甲乙丙：三人各 100，与改成「全部」时结果相同 |
| 6 | 例 5 再加成员丁：这笔仍只在甲乙丙之间分，丁的 `borne` 不含它 |
| 7 | 两人账本、没有多人归属：与改动前的输出逐字段相同（保留一份改动前的输出做对比） |
| 8 | 甲付 100、乙付 100，都归属甲乙丙：承担 66.67 / 66.67 / 66.66，`lines` 为丙分别转给甲、乙 33.33 |

再补两项：

- 指定支出类型规则：给某类型配一条规则，记一笔该类型 101 元、归属甲乙丙的支出。三人有效收入分别被扣 33.67、33.67、33.66。
- 支出结构：对例 8，每人 `pies.members[].slices` 的金额之和等于他的承担额。

## 2. 电脑端记账

1. 新增支出，归属人选甲、乙，保存。时间线上这笔显示「甲、乙」，卡片是淡紫色底。
2. 已选乙时再选「全部」，乙被清掉；已选「全部」时再选甲，「全部」被清掉。全部清空后保存，按「全部」保存。
3. 归属人选甲、乙、丙并保存：显示「甲、乙、丙」，不是「全部」。
4. 切到收入：归属人选择里没有「全部」，只能选一人。不选就保存，提示收入必须选一名归属人。
5. 编辑例 1 的那笔：归属人回显甲、乙。只改金额保存，归属人不变。改成只选乙保存，时间线只显示乙。
6. 用乙的账号编辑甲记的这笔，提示「只能编辑自己记的账单」。

## 3. 小程序记账

1. 记一笔：归属人区域平铺「全部」和甲、乙、丙标签。点甲、乙，完成，流水显示「甲、乙」并使用淡紫底色。
2. 再次进入记一笔：默认已选甲、乙。填金额后点「再记一笔」，金额、描述、照片被清空，日期和甲、乙保留，且不产生记账。
3. 已选甲、乙时切到收入：标签里没有「全部」，归属人变为自己，并有提示。只选了乙时切到收入，仍是乙。
4. 上一次记的是多人或「全部」，这次记收入：默认是自己。上一次记的是单人乙，这次记收入：默认是乙。
5. 编辑一笔归属甲、乙的支出：标签回显甲、乙。只改金额保存，名单不变。

## 4. 搜索与导出

在已有「甲、乙」多人支出、单人支出和「全部」支出的账本上：

| 操作 | 预期 |
|------|------|
| 电脑端搜索，归属人选「乙」 | 出现「甲、乙」这笔 |
| 电脑端搜索，归属人选「丙」 | 不出现「甲、乙」这笔 |
| 电脑端搜索，归属人选「全部」 | 不限归属人，三种记账都出现 |
| 小程序搜索，同上三种条件 | 结果与电脑端逐条一致（SC-009） |
| 电脑端导出明细 | 「归属人」列为「甲、乙」 |

## 5. 概览

1. 记规格 US2 例 4 的三笔，查询。结算文案与第 1 节例 4 一致。
2. 点乙的支出结构里多人支出所在的类型：明细里有这笔，金额是原记账金额 200。点丙的同一类型：没有这笔。
3. 左侧收入明细、总支出、总投资、总消费、总收入、近三年趋势：与改动前相同。

## 6. 服务端校验

用接口工具直接请求（不经过界面）：

| 请求 | 预期 `message` |
|------|----------------|
| 新增收入，`belongUserIds: []` | 收入只能选一名归属人 |
| 新增收入，`belongUserIds` 两人 | 收入只能选一名归属人 |
| 新增支出，只传 `belongUserId: "id乙"`（旧客户端写法） | 当前版本过旧，请更新后再记账；数据库没有新增记录 |
| 编辑支出，只传 `belongUserId`（旧客户端写法） | 当前版本过旧，请更新后再记账；原记录不变 |
| 新增支出，`belongUserId` 和 `belongUserIds` 都传 | 以 `belongUserIds` 为准 |
| 新增支出，两个字段都不传 | 归属人列表无效 |
| 新增支出，`belongUserIds` 含重复 id | 归属人不能重复 |
| 新增支出，`belongUserIds` 含非成员 id | 归属人不是该账本成员 |
| 列表，只传 `belongUserId: "id乙"`（旧客户端写法） | 不报错，按不限归属人返回 |
| 列表、汇总的响应 | 每项有 `belongUserIds`，没有 `belongUserId` |

结算接口 `quantityInputs[].belongUserId` 照旧可用，不受影响。

另在数据库里核对：上面「甲、乙」那笔的 `belong_user_id` 为 `id甲,id乙`（按 `bill_users.id` 升序），`belong_user_name` 为 `甲、乙`。先勾乙再勾甲保存的记账，存出来的值与之相同。

## 6.1 升级与回滚演练

在一份线上库的副本上：

1. 执行升级脚本，旧版本服务端照常记账、查询，没有报错。
2. 发布新版本，记一笔多人支出。
3. 导出 `belong_user_id LIKE '%,%'` 的行，执行回滚脚本：这笔变为「全部」，两列改回 36、64，旧版本服务端正常运行。
4. 再执行一次升级脚本，确认可以重复执行。
5. 成套回滚（FR-022）：在体验环境同时把服务端回退到旧版本、把小程序切回旧版本，记一笔单人支出，归属人仍是这名成员，不会变成「全部」。

## 6.2 小程序版本过渡

1. 用旧版本小程序（体验版保留一份）连新服务端记一笔支出：提示「当前版本过旧，请更新后再记账」，没有写入记录。
2. 上传新版本后，旧版本冷启动：弹出不可取消的更新提示，确认后重启到新版本，可以正常记账。
3. 新版本第一次打开记一笔：上次用旧版本记的归属人（旧缓存里的 `belongUserId`）能正确作为默认值。

## 7. 回归

- 没有任何多人归属支出的两人、三人账本，各查询至少 5 组区间：概览结果与改动前完全一致（SC-004）。
- 预算的当年支出、照片上传与查看、导入 Excel、批量解析录入：行为不变。
- 手机网页不做验收（FR-018）。已知上线后它的新增和编辑会被拒绝。
